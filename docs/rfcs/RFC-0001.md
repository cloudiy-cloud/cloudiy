## Abstract

This document defines the vision, philosophy and long-term direction of the Compute Protocol.

The Compute Protocol is an open protocol for computational resource allocation.

It enables independent participants to contribute computational resources and allows any identity to consume those resources through a universal and implementation-independent interface.

Unlike traditional cloud providers, the Compute Protocol does not define a centralized service.

Instead, it defines a common language for discovering, allocating and executing computational workloads across heterogeneous infrastructure.

The reference implementation described throughout this specification is only one possible implementation of the protocol.

The protocol itself is intended to remain independent of any company, implementation, runtime, programming language or blockchain.

## Status of this Memo

This document is informational.

It defines the philosophy of the protocol rather than its implementation.

Future RFCs will formally define protocol messages, APIs, scheduling rules and provider responsibilities.

## 1. Introduction

Modern computing has evolved through several important abstractions.

Physical hardware became virtual machines. Virtual machines became containers. Containers became cloud services. Cloud services became APIs.

Artificial Intelligence introduced autonomous software capable of making decisions without human intervention.

Despite these advances, computational infrastructure remains fragmented.

Every cloud provider exposes different APIs. Every compute marketplace defines different abstractions. Every scheduler implements proprietary allocation mechanisms. Every provider defines different provisioning workflows.

Developers continuously rewrite infrastructure code whenever changing providers. Applications remain coupled to specific cloud vendors. AI agents cannot seamlessly negotiate computational resources across independent providers.

The Compute Protocol exists to eliminate this fragmentation.

Rather than defining another cloud platform, it defines a common protocol for computational resource allocation.

---

## 2. Motivation

Information became universally accessible after the standardization of HTTP. Communication became universally accessible after TCP/IP. Email became universally accessible after SMTP. Container images became portable through OCI.

Computational resources, however, remain isolated inside proprietary ecosystems.

Today, applications request infrastructure using vendor-specific APIs. An application written for one provider often requires significant modification before it can execute on another. This creates unnecessary friction for developers, organizations and autonomous systems.

The protocol addresses this problem by introducing a universal abstraction for computational resources.

Applications should request computation. The protocol determines how computation is allocated.

---

## 3. The Compute Problem

Historically, infrastructure has been organized around machines.

Users rent servers. Users rent virtual machines. Users rent GPUs. Users configure operating systems. Users manage networking. Users install drivers. Users maintain infrastructure.

These responsibilities belong to infrastructure providers rather than application developers.

The protocol proposes a different abstraction.

Applications should never request machines. Applications should request **work**. The protocol allocates resources necessary to execute that work.

The underlying infrastructure becomes an implementation detail.

---

## 4. Vision

The Internet connected computers. Blockchain connected value. Artificial Intelligence connected intelligence.

The next logical step is connecting **computation**.

The Compute Protocol aims to become the universal language through which computational resources are described, discovered, allocated and consumed.

Any participant may contribute resources. Any participant may consume resources. Any implementation may participate. Any runtime may execute workloads.

The protocol intentionally avoids dependence on specific hardware vendors, operating systems, runtime technologies or economic models.

Its purpose is interoperability rather than ownership.

---

## 5. Core Philosophy

The protocol is founded on several principles.

### 5.1 Computation is a Resource

Computation is not synonymous with servers. Computation is not synonymous with GPUs.

Computation consists of independent resources including processing power, memory, storage, networking and hardware acceleration.

Resources should be described independently rather than bundled into predefined machine types.

### 5.2 Infrastructure Must Disappear

Applications should never be required to understand infrastructure.

Developers describe requirements. The protocol allocates resources. Infrastructure becomes invisible.

### 5.3 Workloads Over Machines

Machines represent physical implementation. Workloads represent user intent.

The protocol prioritizes workloads. Infrastructure exists only to satisfy workloads.

### 5.4 Implementation Independence

The protocol does not require Docker. The protocol does not require Kubernetes. The protocol does not require Linux. The protocol does not require Solana.

The protocol defines abstractions rather than implementations. Individual implementations remain free to evolve independently.

### 5.5 Open Participation

Any participant capable of executing workloads may become a provider.

Providers are not limited to datacenters. Providers may include:

* Personal computers
* Enterprise servers
* GPU clusters
* Universities
* Research laboratories
* Cloud providers
* Future compute providers

The protocol intentionally avoids assumptions regarding provider ownership.

### 5.6 Universal Identities

The protocol recognizes only identities.

Identities may represent:

* Humans
* Organizations
* AI Agents
* Autonomous Software
* DAOs
* Backend Services
* Other Protocols

The protocol never distinguishes between them. All identities interact through identical interfaces.

### 5.7 Open Standards First

Whenever possible, existing open standards should be adopted. The protocol should not redefine concepts already standardized elsewhere.

Examples include: OCI, Docker Images, OpenAPI, OAuth, TLS, HTTP, WebSocket.

Future RFCs may reference additional standards.

### 5.8 Long-Term Objective

The ultimate objective is not building another cloud platform.

The objective is creating a universal protocol for computational resource allocation.

Cloud providers may implement it. Independent providers may implement it. Organizations may implement it. Open-source communities may implement it.

Applications should eventually execute workloads without requiring knowledge of the underlying infrastructure provider.

In the same way applications rarely consider how HTTP packets travel across the Internet, future applications should rarely consider where computation is physically executed.

---

## 6. Conceptual Model

The Compute Protocol introduces a set of fundamental abstractions. These abstractions define the vocabulary of the protocol.

Implementations may differ internally, but all compatible implementations should preserve these concepts.

The protocol is built around six primary entities:

1. Identity
2. Resource
3. Capability
4. Provider
5. Workload
6. Environment

Together, these entities describe the complete lifecycle of computation.

---

## 7. Identity

### Definition

An Identity represents any entity capable of interacting with the Compute Protocol. An Identity is the fundamental actor of the network.

The protocol does not classify identities based on whether they are human-operated or autonomous. A human user, an AI agent, a company backend, or another protocol are all equivalent from the perspective of the protocol.

### Identity Responsibilities

An Identity may:

* Request computational resources.
* Create workloads.
* Provide computational resources.
* Publish execution templates.
* Publish container images.
* Execute automated workflows.
* Pay for consumed resources.
* Receive compensation for provided resources.

### Identity Examples

**Human Identity** — a developer creating an AI application:

```text
Identity:  Developer Account
Actions:   Create Environment · Deploy Application · Monitor Workload
```

**AI Agent Identity** — an autonomous software agent requiring additional compute:

```text
Identity:  AI Agent
Actions:   Request GPU · Execute Training · Release Resources
```

The protocol does not need to know that the caller is an AI agent.

**Organization Identity** — a company operating thousands of compute nodes:

```text
Identity:  Company
Resources: 500 GPU Nodes · 200 TB Storage
```

---

## 8. Resource Model

### Definition

A Resource represents a measurable computational capability available for allocation.

The protocol does not treat computers as indivisible units. Instead, computers expose resources.

### Resource Categories

**CPU Resource** — processing capability. Properties: core count, architecture, frequency, benchmark score, availability.

```json
{ "type": "cpu", "cores": 16, "architecture": "x86_64" }
```

**Memory Resource** — volatile memory. Properties: capacity, bandwidth, availability.

```json
{ "type": "memory", "capacity": "64GB" }
```

**GPU Resource** — hardware acceleration. Properties: manufacturer, model, VRAM, CUDA capability, compute capability, availability.

```json
{ "type": "gpu", "model": "RTX 4090", "vram": "24GB" }
```

**Storage Resource** — persistent or temporary storage. Properties: capacity, type, speed, availability. Examples: NVMe SSD, SATA SSD, HDD, Network Storage.

**Network Resource** — connectivity. Properties: bandwidth, latency, region, reliability.

### Resource Independence

Resources are independent. A provider does not need to expose all resource types.

A GPU-only provider (`8 × RTX 4090`), a CPU provider (`128 cores`), a storage provider (`100 TB NVMe`) and a hybrid provider (CPU + RAM + GPU + Storage + Network) are all valid.

The protocol must support all cases.

---

## 9. Capability Model

### Definition

Resources describe **quantity**. Capabilities describe **functionality**.

A capability represents a feature, compatibility layer or software environment available on a provider.

### Examples of Capabilities

* Hardware: `CUDA 12.8`, `ROCm`, `OpenCL`, `Vulkan`, `AVX512`
* Software: `Docker`, `Podman`, `Kubernetes`, `Python`, `Rust`, `Node.js`
* AI: `PyTorch`, `TensorFlow`, `Ollama`, `vLLM`, `ComfyUI`, `Whisper`
* Operating systems / architectures: `Linux`, `Windows`, `ARM64`, `x86_64`

### Capability-Based Scheduling

Consumers should describe requirements using capabilities.

Instead of *"I need machine #123"*, a workload requests:

```text
Need: CUDA >= 12 · PyTorch · Linux · GPU VRAM >= 24GB
```

The scheduler discovers compatible providers.

---

## 10. Provider Model

### Definition

A Provider is an Identity that contributes computational resources to the network. Providers transform private hardware into available network resources.

### Provider Responsibilities

A provider must:

* Advertise available resources.
* Maintain resource availability.
* Execute workloads securely.
* Report health metrics.
* Maintain communication with the network.
* Respect resource allocation rules.

### Provider Types

* **Personal Provider** — a user sharing unused GPU capacity (`RTX 4090 · available 8 hours/day`).
* **Professional Provider** — a company operating servers (`100 GPU nodes · 99.9% uptime`).
* **Specialized Provider** — research infrastructure (high-memory nodes, specialized accelerators).

---

## 11. Workload Model

### Definition

A Workload represents a request to execute computation.

A workload describes:

* What should execute.
* What resources are required.
* How long execution should exist.
* What output is expected.

### Workload Example

```yaml
workload:
  image: pytorch-training
  resources:
    cpu:
      cores: 16
    memory:
      size: 64GB
    gpu:
      count: 2
      vram: 48GB
  storage:
    persistent:
      size: 200GB
  command: python train.py
```

### Workload Lifecycle

A workload moves through defined states:

```text
REQUESTED → SCHEDULED → ALLOCATED → RUNNING → COMPLETED → RELEASED
```

Failure states: `FAILED`, `CANCELLED`, `TIMEOUT`.

---

## 12. Compute Environment

### Definition

A Compute Environment is the execution context created to run a workload.

The user interacts with environments. The infrastructure creates them.

### Environment Components

An environment may contain: operating system, runtime, container image, CPU allocation, memory allocation, GPU allocation, storage mounts, network access, environment variables, secrets, ports.

### Example

A user requests:

```text
Environment: Ubuntu 24.04 · Python · CUDA · PyTorch · RTX 4090 · 32GB RAM · SSH Access
```

The protocol decides: where it runs, how it runs, which runtime is used.

---

## 13. Runtime Model

### Definition

A Runtime executes environments. The protocol separates execution from abstraction.

The protocol defines: *"Run this workload."*
The runtime defines: *"How this workload executes."*

### Supported Future Runtimes

Initial: Docker.
Future: Firecracker, Kata Containers, WASM, MicroVMs, Kubernetes Pods.

### Docker Position

Docker is the first implementation choice. Docker is **not** part of the protocol specification. The protocol must survive beyond Docker.

---

## 14. Compute Recipes

### Definition

A Compute Recipe is a reusable description of an environment. Recipes simplify workload creation.

```yaml
recipe:
  name: AI Development Environment
  requirements:
    GPU:
      VRAM:
        minimum: 24GB
  software:
    - CUDA
    - PyTorch
    - Python
    - Jupyter
```

### Recipe Benefits

Recipes enable: reproducibility, community sharing, faster deployment, standardized environments.

---

## 15. Compute Images

Images represent executable software environments.

Examples: Ubuntu, PyTorch, Ollama, Stable Diffusion, Rust Development, Node.js.

Images may come from: public registries, private organizations, community creators.

## 16. Protocol Goals

The Compute Protocol exists to solve a fundamental infrastructure problem: the absence of a universal communication layer for computational resources.

### 16.1 Universal Compute Access

The protocol should allow any identity to access computational resources without being coupled to a specific provider.

A consumer should not need to know: who owns the hardware, where the hardware is located, which operating system is running, which infrastructure provider is executing the workload.

The consumer only describes the required computation:

```yaml
request:
  gpu:
    vram: 24GB
  cpu:
    cores: 8
  memory:
    size: 32GB
  capabilities:
    - CUDA
    - PyTorch
```

The protocol resolves execution.

### 16.2 Provider Neutrality

The protocol must not favor any provider type. A home computer, a data center, an enterprise cluster or a cloud provider should all be able to participate. The protocol creates a common language between providers.

### 16.3 Hardware Agnosticism

The protocol must support current and future computational hardware.

Today: CPUs, GPUs. Tomorrow: NPUs, TPUs, quantum accelerators, specialized AI chips.

The protocol should not require architectural redesign when new hardware emerges.

### 16.4 Workload Portability

A workload created for one provider should be executable on another compatible provider.

Portability should be achieved through: standardized descriptions, container images, capabilities, environment specifications.

### 16.5 Autonomous Compute Allocation

The protocol should enable software agents to acquire computational resources autonomously.

An agent should be able to:

1. Evaluate its requirements.
2. Request resources.
3. Execute computation.
4. Release resources.
5. Continue operation.

No human intervention should be required.

### 16.6 Efficient Resource Utilization

A significant amount of computational capacity remains unused worldwide: idle gaming computers, unused workstation GPUs, enterprise servers during off-hours, research infrastructure.

The protocol should transform unused capacity into a globally available computational resource.

### 16.7 Open Innovation

The protocol should allow anyone to build: providers, schedulers, applications, SDKs, marketplaces, developer tools.

The protocol should create an ecosystem, not a single application.

---

## 17. Protocol Non-Goals

Defining what the protocol does **not** attempt to become is equally important.

### 17.1 Not a Cloud Provider

The protocol does not operate as a centralized cloud company. It does not own all infrastructure. It does not require proprietary data centers.

### 17.2 Not a Hardware Marketplace

The protocol does not sell GPUs, CPUs or computers. Hardware is only the source of computational resources.

### 17.3 Not an AI Agent Marketplace

The protocol does not compete with AI applications. Agents are consumers of computation. The protocol provides infrastructure for them.

### 17.4 Not a Single Runtime Platform

The protocol does not depend permanently on Docker, Kubernetes or any execution technology. The abstraction must survive technological evolution.

### 17.5 Not a Blockchain Application

Blockchain may provide useful mechanisms for payments, identity, reputation and settlement.

However, blockchain is not the purpose of the protocol. The purpose is computation.

## 18. Architectural Principles

### 18.1 Separation of Protocol and Implementation

The protocol specification must remain independent from implementation. Multiple implementations should be possible.

Implementation A: Rust daemon. Implementation B: Go daemon. Implementation C: enterprise Kubernetes adapter.

All should communicate using the same protocol.

### 18.2 API First Design

The primary interface of the protocol is not the user interface. The primary interface is the API.

Human interfaces are optional. Software interfaces are fundamental.

The protocol is designed primarily for: applications, services, automation, AI agents.

### 18.3 Agent-Native Architecture

AI agents should be considered first-class participants. The protocol should enable autonomous decision making.

An agent should be able to: estimate required resources, compare available options, allocate computation, monitor execution, terminate resources.

The protocol should treat this as a normal operation.

### 18.4 Ephemeral Computing

Computational environments should exist only when necessary.

The default lifecycle should be: **Create. Execute. Complete. Destroy.**

Resources return to the network. This prevents unnecessary infrastructure waste.

### 18.5 Resource Composition

Resources should be composable. A workload may require:

```text
CPU + Memory + GPU + Storage + Network + Capabilities
```

The scheduler combines these requirements into an execution environment.

### 18.6 Security by Isolation

Untrusted workloads must never directly access provider systems. Isolation is mandatory.

The protocol assumes: workloads may be malicious, workloads may fail, workloads may consume unexpected resources.

Security mechanisms must be built into the architecture.

---

## 19. Why Docker Is an Implementation Detail

Containers represent one of the most important advances in software deployment. They solved application portability. However, containers are not the final abstraction.

The protocol should define *"what needs to run"*, not *"how it runs"*.

Docker is currently the most practical execution layer because it provides maturity, ecosystem, portability, hardware support and community adoption.

However, future execution models may replace or complement Docker. The protocol must remain runtime-independent.

---

## 20. Why Blockchain Is an Implementation Layer

Blockchain introduces useful primitives: decentralized identity, programmable payments, transparent settlement, reputation systems.

However, computational networks existed before blockchain.

The protocol should first solve: resource discovery, scheduling, execution, reliability, interoperability.

Economic systems can be layered afterward. The protocol must remain useful even without blockchain.

---

## 21. AI Agents as First-Class Citizens

Artificial intelligence introduces a new category of compute consumer.

Traditional software waits for human instructions. Agents can reason, plan, execute and adapt. This creates a new infrastructure requirement: agents need the ability to dynamically acquire resources.

Example — an AI coding agent receives a task. It determines:

```text
Need: 32 CPU cores · 64GB RAM · GPU acceleration · Rust environment
```

The agent requests resources. The protocol creates an environment. The agent completes the task. Resources are released.

This workflow should be native.

---

## 22. The Future Compute Economy

The current internet connects information. Future infrastructure must connect computation.

A global compute economy may contain: millions of providers, billions of devices, autonomous consumers, dynamic resource markets.

The protocol provides the communication layer.

---

## 23. Final Vision

The Compute Protocol represents a shift in how humanity interacts with computation.

Today: humans manage computers.
Tomorrow: applications request computation.

The future should not require users or agents to understand servers. They should express intent. The protocol should transform intent into execution.

The fundamental abstraction is:

```text
Identity
   |
   | requests
   v
Workload
   |
   | requires
   v
Resources + Capabilities
   |
   | allocated by
   v
Compute Network
   |
   | executed through
   v
Runtime Environment
```

---

## Conclusion

The Compute Protocol is an attempt to create the missing abstraction layer between software intelligence and physical computation.

The Internet made information globally accessible. Blockchain made value globally transferable. Artificial intelligence made intelligence increasingly autonomous.

The next infrastructure layer is computation itself.

The objective is not to build another cloud provider. The objective is to create an open protocol where any identity can provide computation and any identity can consume it.

A world where applications do not ask *"Which server should I use?"* but simply declare *"I need computation."*

And the network responds.
